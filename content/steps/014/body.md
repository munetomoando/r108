## 問い

そらまめマーケット経営企画部のあなたは、ネット通販の担当者から「どのカテゴリがいちばん売れているのか」と聞かれました。ところが、注文明細 `orders` には商品ID はあっても、カテゴリは書かれていません。カテゴリは商品マスタ `products` のほうにあります。2つの表をつなげて、カテゴリ別の売上を求めます（会社もデータも架空のものです）。

## 表はなぜ分かれているのか

まず3つの表を眺めましょう。

```r
glimpse(orders)
glimpse(products)
glimpse(customers)
```

`orders` は注文の明細で、1行が「ある注文で、ある商品を何個、いくらで買ったか」です。`products` は商品200点の一覧、`customers` は顧客の一覧です。このように、何度も出てくる情報（商品のカテゴリや顧客の年齢）は別の表に1回だけ書き、明細にはIDだけを書いておくのが会社のデータのふつうの形です。IDのように、表と表をつなぐ手がかりになる列を**キー**と呼びます。

## left_join()：左の表に列を付け足す

`orders` にカテゴリを付けるには、`left_join()` を使います。join は「つなぐ」という意味です。

```r
orders_p <- left_join(orders, products, by = "product_id")
glimpse(orders_p)
```

`left_join(左の表, 右の表, by = "キーの列名")` の形です。左の表の各行について、右の表から product_id が同じ行を探し、その列（category・list_price・unit_cost）を横に付け足します。左の表の行はすべて残り、並び順も変わりません。右の表に相手が見つからない行は、付け足した列が `NA`（値がないこと）になります。

結合したら、第6ステップの `group_by()` と `summarise()` で集計できます。売上は「数量 × 販売単価」です。

```r
orders_p |>
  mutate(sales = qty * unit_price) |>
  group_by(category) |>
  summarise(sales = sum(sales))
```

ここで、定価の `list_price` ではなく、実際に売れた値段の `unit_price` を使うことに注意してください。クーポンを使った注文は定価の8割で売れています。定価で計算すると、売上を実際より多く見積もってしまいます。

## inner_join() と anti_join()：残す行を変える

結合の関数は、どの行を残すかで使い分けます。

- `left_join(x, y)` … x の行をすべて残す
- `inner_join(x, y)` … x と y の両方にキーがある行だけを残す
- `anti_join(x, y)` … y に相手が**見つからない** x の行だけを残す（列は付け足さない）

`anti_join()` は、データの点検に役立ちます。たとえば、顧客マスタに載っていない顧客の注文がないかを調べられます。

```r
anti_join(orders, customers, by = "customer_id")
```

結果が0行でなければ、マスタが古い、退会した顧客の記録が消されている、などの事情が考えられます。顧客の年齢で集計する前に、こうした行がいくつあるかを知っておく必要があります。左右を入れ替えた `anti_join(customers, orders, by = "customer_id")` は「1回も注文していない顧客」を探すことになり、意味が変わります。

## 結合の前後で行数を確かめる

結合は便利ですが、思わぬ形で行数が変わることがあります。`inner_join()` では相手のない行が消えます。また、右の表に同じキーの行が2つ以上あると、左の1行が2行以上に増えます。結合したら `nrow()` で行数を確かめ、元の表と比べる習慣をつけましょう。

```r
nrow(orders)
nrow(orders_p)
```

## 卒論・実務での使いどころ

売上の明細に商品や顧客の情報を結合する作業は実務の分析の大半を占め、卒論でも「都道府県コードで人口のデータを付ける」ように、複数の統計をキーでつなぐ場面で必ず使います。
