## 問い

最後のステップです。そらまめマーケット（架空の会社）に入って1年、上司から「次の経営会議で、自分で見つけたテーマを1つ報告してほしい」と頼まれました。問いを立てるのも、データを選ぶのも、分析の方法を決めるのも自分です。これまでの107ステップで学んだことを使い、**問い → 分析 → 報告書 → 共有** を一人でやり通します。できあがったものは、そのまま就職活動や卒論のゼミで見せられる作品になります。

## 問いを立てる

良い問いは、**答えが出たら誰かの判断が変わる**問いです。「売上の推移を見る」は問いではありません。「〇〇は△△か」の形の疑問文にし、記述・予測・因果のどれを問うのか（第46・91ステップ）を決めます。たとえば `ec_*` なら、次のような問いが立てられます。

- 広告経由で入った顧客は、ほかの経路の顧客より買う額が少ないか（記述。広告費の配分を決める）
- 会員ランクの高い顧客ほど、クーポンで買う量が増えるか（第89ステップの弾力性を顧客の層で比べる）
- 初回購入の月が12月の顧客は、ほかの月の顧客より早く離れるか（第85ステップのコホート分析）

`store_sales_daily`・`churn` や、第2部・第6部の公的統計（`pref_panel` など）、e-Stat から自分で取った統計表を使っても構いません。社外秘のデータ（`ec_*`・`sora_stores` など）は GitHub に送らないので、公開データでも同じく `data/` に置き、README に入手方法を書きます。

## 例：広告経由の顧客は買う額が少ないか

1つ目の問いを例に、分析の芯の部分を示します。2024年までに登録した顧客について、2025年の購入額（買わなかった人は0円）を流入経路で比べます。

```r
spend <- orders |>
  filter(year(order_date) == 2025) |>
  group_by(customer_id) |>
  summarise(sales = sum(qty * unit_price))
cust <- customers |>
  filter(signup_date < ymd("2025-01-01")) |>
  left_join(spend, by = "customer_id") |>
  mutate(sales = replace_na(sales, 0),
         channel = fct_relevel(channel, "検索"))
m2 <- lm(sales ~ channel + age, data = cust)
```

対象は3,902人で、平均購入額は検索経由が20,052円、広告経由が16,163円、紹介経由が25,056円です。年齢をそろえた `m2` では、広告経由は検索経由より約3,885円少なく、95%信頼区間は −5,063円〜−2,708円です。ここで `m2` に会員ランク（`rank`）を加えると、差は −477円に縮み、0と区別できなくなります。ランクは購入額の結果として決まるので、入れると「買う額が少ない」という差そのものを消してしまいます。何を説明変数に入れるかは、問いに照らして決めます。また、流入経路は顧客が選んだもので、無作為に割り当てたわけではありません。結論には「広告が購入額を減らした」ではなく「広告経由で入った顧客は購入額が少ない」と書き、確かめるための次の一手（たとえば広告経由の新規客に初回クーポンを出す A/B テスト）を添えます。

## 手順

1. **プロジェクトを作る。** RStudio は「File」→「New Project...」→「New Directory」→「New Project」で、名前を `r108_final` にします（Positron は「File」→「New Folder from Template...」）。`data` フォルダを作り、使うデータを入れます。`ec_*` なら [ec_orders.csv](data/ec_orders.csv)・[ec_customers.csv](data/ec_customers.csv)・[ec_products.csv](data/ec_products.csv) をダウンロードして入れます。
2. **Git を始める。** ターミナルで `git init` を実行し、第104ステップと同じ `.gitignore`（`.Rproj.user/`・`.Rhistory`・`.RData`・`data/`・`.Renviron`）を書いて、`.gitignore` と `.Rproj` をコミットします（1つ目）。
3. **雛形を置く。** [final.qmd](local/final.qmd) をダウンロードしてプロジェクトのフォルダに移し、何も変えずに Render（Positron は Preview）します。`final.html` ができれば準備完了です。Windows はエクスプローラー、macOS は Finder で `final.html` をダブルクリックすると、ブラウザで開きます。
4. **少しずつ書いて、そのたびにコミットする。** たとえば「データを読んで整える」「図を足す」「モデルと表を足す」「要約と結論を書く」のように、ひとまとまりごとに `git add final.qmd` と `git commit -m "説明"` で記録します。数字が変わる変更は、必ずコミットを分けます。
5. **README を書く。** 見出しを「問い」「データ」「結論」「作り方」にし、データの入手方法と、Render で `final.html` を作る手順を書いてコミットします。
6. **GitHub に送る。** GitHub で **Private** の空のリポジトリ `r108_final` を作り、第105ステップと同じく `git remote add origin https://github.com/あなたのID/r108_final.git`、`git push -u origin main` で送ります。リポジトリのページで、`data` フォルダがないことを目で確かめます。
7. **確かめる。** R を再起動してから Render し直し、下の点検表で見直してから、確認スクリプトを実行します。直したら、コミットして push してから、もう一度実行します。

`final.html` をリポジトリに入れるかは自分で決めて構いません。入れると、データを持たない人も GitHub から結果を見られます。図や表に社外秘の数字が出ているなら、上司に確かめてからにします。

## 合格の基準

次の2つがそろえば、108ステップの修了です。

**(1) 確認スクリプトの全項目に ✓ が付く。** 確かめるのは、`final.qmd` の題名と名前、形式（html か dashboard）、レポートなら最初の見出しが「要約」で「問い」の節があること、モデル1つ以上とその表、図を描くチャンク3つ以上、`setwd()` や絶対パスを使っていないこと、HTML へのレンダリングと HTML の中の図3つ以上・表1つ以上、README の見出しと200字以上の説明、コミット5つ以上、`data/` と `.Renviron` が除外され履歴にもないこと、トークンらしい文字列がないこと、最新のコミットまで push してあること、コミットしていない変更がないことです。

**(2) 下の点検表のすべてに「はい」と答えられる。**

## 自分で見直す点検表

**問いと結論**
- □ 問いを1文の疑問文で書き、答えが出たら誰の何の判断が変わるかを書いている
- □ 要約の1行目が問いへの答えで、数値はインラインコードで埋め込んでいる
- □ 結論に、前提や限界（因果と言えるか、データの範囲）と、次の一手を書いている

**分析**
- □ データの出所・期間・観測の単位・観測数を書き、除いた行や結合の方法を説明している
- □ 図の軸に単位があり、図ごとに何が言えるかを本文で1〜2文で述べている
- □ 係数を単位つきの言葉で読み、0と区別できるかと、事業として大きいかの両方を述べている
- □ 結果として決まる変数（例：会員ランク）を説明変数に入れていない

**再現と共有**
- □ R を再起動してから Render しても、同じ報告書ができる
- □ README を読めば、他の人がデータを用意して同じ報告書を作れる
- □ 個人情報・社外秘のデータ・API キーを GitHub に送っていない
