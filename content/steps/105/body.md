## 問い

第104ステップで、`sora_app` の履歴を自分の PC に残せるようになりました。次は、同じ部の先輩にアプリのコードを見てもらい、直してもらうことになりました。メールに app.R を付けて送り合うと、どれが最新か分からなくなります。このステップでは、リポジトリをインターネット上に置いて共有するサービス **GitHub** に送ります。その前に、**何を送ってよく、何を送ってはいけないか**を判断します。

## 公開してよいもの、いけないもの

GitHub に送ったものは、後でファイルを消しても、履歴から読めます。送る前に判断します。

| 送ってよい | 送ってはいけない |
| --- | --- |
| 自分で書いたコード（app.R、分析のスクリプト） | 個人情報（顧客の名前・住所・購入履歴、アンケートの個票） |
| README、`.gitignore` | API キー、パスワード、アクセストークン（`.Renviron`） |
| 再配布が認められた公開データ（出所を明記） | 社外秘のデータ（店舗の売上、未公表の数字） |
| 図や表のうち、公表してよいと決まったもの | 利用の約束で再配布が禁じられたデータ（購入したデータ、大学が契約したデータベース、申請して借りた個票データ） |

政府統計（e-Stat など）の多くは、出所を明記すれば再配布できます。一方、大学の図書館の契約で使える企業財務のデータベースのように、使ってよくても配ってはいけないデータもあります。迷ったら送らず、README に入手方法を書きます。

GitHub のリポジトリには、誰でも見られる **公開**（Public）と、招待した人だけが見られる **非公開**（Private）があります。会社や卒論の分析は、まず非公開で作ります。公開してよいかは、上司や指導教員と相談して決めます。

## README を書く

README（リードミー）は、リポジトリを開いた人が最初に読む説明書で、GitHub ではリポジトリのページの下に表示されます。Markdown（第51ステップ）で書きます。最低限、次の3つを書きます。

```markdown
# そらまめマーケット 地域別売上アプリ

そらまめマーケット（架空の会社）の店舗の日次売上から、地域を選ぶと
その地域の月別売上の図と、店舗別の2025年の売上の表を出す Shiny アプリです。

## 動かし方

1. `data` フォルダに `sora_stores.csv` と `store_sales_daily.csv` を置きます。
2. RStudio で `app.R` を開き、「Run App」を押します。

## データについて

店舗の売上は社外秘のため、このリポジトリには含めていません（`.gitignore` で
`data/` を除外しています）。データは社内の共有フォルダから入手してください。
```

## 手順

1. **README.md を書いてコミットする。** RStudio の「File」→「New File」→「Markdown File」で上の内容を書き、プロジェクトの一番上に `README.md` として保存します。ターミナルで `git add README.md` と `git commit -m "README を書く"` を実行します。
2. **GitHub のアカウントを作る。** https://github.com/ の「Sign up」から作ります。ユーザー名は、就職後も使える名前にしておくと便利です。メールアドレスを公開したくなければ、GitHub の「Settings」→「Emails」で「Keep my email addresses private」に印を付け、表示される `...@users.noreply.github.com` のアドレスを `git config --global user.email` に設定し直します。
3. **空のリポジトリを作る。** GitHub の右上の「+」→「New repository」で、名前を `sora_app` にし、**Private** を選びます。README・.gitignore・ライセンスを足す欄には印を付けません（手元にあるものと食い違うのを防ぐため、空で作ります）。
4. **リモートを登録して送る。** 作ったリポジトリのページに出る URL（`https://github.com/あなたのID/sora_app.git`）を使い、ターミナルで次を実行します。手元のリポジトリから見た GitHub 側のリポジトリを**リモート**といい、`origin` という名前で登録するのが慣例です。

   ```sh
   git remote add origin https://github.com/あなたのID/sora_app.git
   git branch -M main
   git push -u origin main
   ```

5. **認証する。** 初めての push では、GitHub のアカウントの確認を求められます。
   - Windows：Git for Windows に含まれる Git Credential Manager がブラウザを開くので、GitHub にサインインして許可します。次からは聞かれません。
   - macOS：ユーザー名とパスワードを聞かれます。パスワードの欄には、GitHub のパスワードではなく**個人アクセストークン**を貼り付けます。トークンは GitHub の「Settings」→「Developer settings」→「Personal access tokens」→「Fine-grained tokens」→「Generate new token」で作ります。有効期限（例 90日）を決め、「Repository access」で `sora_app` だけを選び、「Permissions」の「Contents」を「Read and write」にします。表示されたトークンは一度しか見られません。macOS のキーチェーンに保存され、次からは聞かれません。
6. **GitHub で確かめる。** リポジトリのページを再読み込みし、`app.R`・`README.md`・`.gitignore` があり、**data フォルダはない** ことを自分の目で確かめます。
7. **その後の流れ。** app.R を直したら、`git commit -am "説明"` のあと `git push` で送ります。RStudio の「Git」タブなら、「Commit」のあと緑の上向き矢印「Push」を押します。

トークンはパスワードと同じです。スクリプト、README、`git remote add` の URL（`https://名前:トークン@github.com/...` の形）には書きません。GitHub CLI（`gh auth login`）や usethis パッケージを使う方法もありますが、ここでは追加のソフトを入れずに済む方法を選びました。

## 間違えて送ってしまったら

API キーやトークンを送ってしまったら、**まずそのキーを発行元のサイトで無効にし（Revoke）、新しいキーを作ります**。履歴から消すより先です。非公開のリポジトリでも同じです。社外秘のデータや個人情報を送ってしまったら、すぐ上司（卒論なら指導教員）に報告し、指示に従います。リポジトリを削除して作り直すことが多いです。

## 自分のPCで確認する

右の欄から `check_105.R` をダウンロードしてプロジェクトのフォルダに置き、コンソールで `source("check_105.R", encoding = "UTF-8")` を実行します。インターネットにはつながず、手元のリポジトリの記録から、README、リモートの設定、push 済みかどうか、機密のファイルやキーらしい文字列がコミットに入っていないかを調べます。

## 卒論・実務での使いどころ

卒論のリポジトリを非公開で GitHub に置き、指導教員を「Settings」→「Collaborators」で招待しておけば、PC が壊れてもコードは残り、先生は最新のコードと README をいつでも見られます。
