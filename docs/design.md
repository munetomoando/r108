## 目的と設計の決定事項

R未経験の経済学部2年生が、ブラウザで108ステップを順にこなすことで、第54ステップで卒論の実証分析を、第108ステップで業務レベルの分析と報告を一人でできるようにする無償の自習アプリを作る。この文書はClaude Codeで実装するための仕様書で、以下の決定事項を前提とする。

| 項目 | 決定 |
| --- | --- |
| 構成 | 4段階 × 3部 × 9ステップ ＝ 12部・108ステップ。各部の第9ステップは総合演習 |
| 1ステップの分量 | 約45分。解説＋動く例＋小課題3〜5問。全小課題に正解で完了 |
| 言語・書き方 | 画面は日本語。Rはtidyverse流儀、パイプはネイティブの `\|>` に統一 |

| 進捗 | ログインなし。ブラウザ保存（キー `r108.v1`）。授業向けの進捗送信は第2版で追加 |

**第1部をビジネスの題材にする理由。** 学生が続けるかどうかは最初の数ステップで決まる。第1部は架空の企業「そらまめマーケット」の店舗データ（`sora_stores`）で、売上・客単価・前年割れといった仕事で使う問いから入り、学ぶことが将来に役立つと実感させる。公的統計は、扱い方そのものが技能になる第2部（取得と整形）と卒論・政策評価の部で本格的に使う。

**第2部以降の事例の選び方。** 次の3つの規則で、ビジネスの題材と公的統計・政策の題材を使い分ける。

1. **技能が汎用のステップはビジネスの題材を優先する。** データの読込・掃除・結合、グラフ、検定の考え方など、どの仕事でも同じように使う技能は、そらまめマーケットのデータか、仕事の場面の問いで教える（第10・12・14・15・22・26・35ステップなど）
2. **公的統計の扱い方そのものが技能のステップは公的統計を使い、問いを仕事の場面に置く。** 例えば家計調査は「出店先を考える」、最低賃金は「パートの時給と人件費を考える」という問いで読む（第11・16・18・25・27ステップ）。データは変えず、本文の導入と結論3行で仕事とのつながりを示す
3. **卒論と政策評価のステップは経済学の題材のままにする。** 第4〜9部（統計・回帰・卒論・因果推論・時系列）は経済学部の卒論で使う力を育てる部で、賃金・職業訓練・最低賃金といった題材はそれ自体が学ぶ内容である。ここは変えない。ただし時系列の部（第9部）は、景気指標を読む力が企業の需要予測や計画づくりにも使えることを本文で示す

**会社の設定。** 「そらまめマーケット」は、食品スーパー50店舗（`sora_stores`）とネット通販（`ec_*`。食品のほか日用品・家電・本なども扱う）を営む架空の小売企業とする。第1部・第2部・第3部の一部、第10〜12部はすべてこの会社の話で、学生は経営企画部の新入社員として入り、第108ステップで一人前の分析担当になる。第11部の日次売上（`store_sales_daily`）は `sora_stores` の30店舗のもので、店舗IDと所在地が一致する。来店客アンケート（`messy_survey`）もこの会社のものとする。

**合成データを多用する理由。** 自動判定には毎回同じ答えが出るデータが必要で、因果推論の練習には「真の効果」が分かっているデータが最も教育効果が高い。公的統計は第2部（取得と整形）と各段階の総合演習で使い、実データの手触りを担保する。

## システム構成

サーバーを持たない静的サイトで、Rの実行・採点・進捗保存はすべて学生のブラウザ内で完結させる。教材の中身（本文・課題・正解・判定）はコードから分離してYAMLとMarkdownで持ち、教員がコードに触れずに改訂できるようにする。

| 図の表示 | webRのcanvasグラフィックス | ggplotの出力を右ペインに表示 |

## ステップのデータ形式と自動判定

1ステップは `step.yaml`（メタ情報・小課題・正解・判定）と `body.md`（解説）の2ファイルで表す。判定は「正解コードを実行して得た結果」と「学生のコードの結果」を比べる方式を基本とし、正解の値をYAMLに直接書かない。

```yaml
id: "013"
part: 2
title: 横長の表を縦長にして県別の推移を比べる
question: 2000年から2020年にかけて、就業率が最も上がった県はどこか？
minutes: 45
mode: browser            # browser | local
packages: [dplyr, tidyr, readr]
data: [pref_labor_wide.csv]
learn: [pivot_longer, pivot_wider]
setup: |
  library(dplyr); library(tidyr); library(readr)
  labor_wide <- read_csv("data/pref_labor_wide.csv", show_col_types = FALSE)
exercises:
  - id: a
    type: fill           # write | fill | predict | fix | interpret
    prompt: labor_wide を縦長にして labor_long に代入してください（列名は year と emp_rate）。
    starter: |
      labor_long <- labor_wide |>
        pivot_longer(___)
    solution: |
      labor_long <- labor_wide |>
        pivot_longer(-pref, names_to = "year", values_to = "emp_rate")
    check: |
      expect_object("labor_long", class = "data.frame")
      expect_df_equal(labor_long, .sol$labor_long, ignore_row_order = TRUE)
    hints:
      - 縦に並べたいのは pref 以外の列です。
      - names_to には新しい列名を文字列で渡します。
      - pivot_longer(-pref, names_to = "year", values_to = "emp_rate")
  - id: b
    type: predict
    prompt: labor_long の行数はいくつになりますか。
    choices: ["47", "5", "235", "282"]
    answer: 3            # 0始まり。47県×5時点
    explain: 横に並んでいた5時点が縦に展開されるので 47 × 5 = 235 行です。
review_of: "012"         # 最後の小課題で前ステップを復習させる
```

**判定の流れ。**

1. ステップを開いたら新しいR環境を作り、`setup` を実行する
2. 別の環境で各小課題の `solution` を実行し、結果を `.sol` として保持する（ステップ内で1回だけ）
3. 学生のコードを実行し、標準出力・図・エラーを取得する
4. 学生の環境で `check` を実行する。判定関数が失敗を出したらその日本語メッセージを表示し、何も出なければ正解
5. Rのエラーは日本語の説明に置き換えて表示する（例：`object 'x' not found` →「オブジェクト x が見つかりません。綴りと、前の行を実行したかを確認しましょう」）

**判定関数（Rパッケージ `r108check`）。** 失敗時は `r108_fail("日本語メッセージ")` を投げる。

| 関数 | 何を確かめるか |
| --- | --- |
| `expect_object(name, class = NULL)` | オブジェクトが存在し、指定のクラスか |
| `expect_value(x, expected, tol = 1e-6)` | 数値・文字が一致するか |
| `expect_df_equal(x, y, ignore_row_order, ignore_col_order = TRUE, tol)` | データフレームが一致するか。違うときは行数・列名・値のどこが違うかを返す |
| `expect_cols(df, cols)` / `expect_nrow(df, n)` | 列名・行数 |
| `expect_ggplot(p = last_plot(), geom, x, y, colour, facet)` | ggplotの層の種類と対応づけ（aes）を確認 |
| `expect_model(m, like = .sol$m, tol = 1e-4)` | 推定方法・式・係数が正解と一致するか（lm、glm、fixest） |
| `expect_coef(m, term, value, tol)` | 特定の係数の値 |
| `expect_uses(fn)` / `expect_not_uses(fn)` | 学生のコードがその関数を使っているか（構文解析で判定） |
| `expect_text(pattern)` | 出力に特定の文字列が含まれるか（解釈の記述課題用） |

**ローカル実行ステップ（11ステップ）。** 第50〜54、100〜102、104〜105、108ステップは学生のPCのRで行う。ステップ画面から確認用スクリプト（例 `check_050.R`）を配り、学生がRStudioかPositronで実行すると、条件（ファイルの存在、Quartoのレンダリング成功、回帰表の有無、`renv.lock` の有無など）を確かめて、合格時だけ修了コード（例 `R108-050-7F3A`）を表示する。アプリには修了コードのSHA-256だけを持たせ、入力されたコードを照合して完了にする。自習用なので、厳密な不正防止はしない。

**主要な生成式（Claude Codeはこの式どおりに実装し、仕込んだ値が推定で再現できることをテストで確認する）。**

- `wage_survey`：log\_wage = a + 0.07×educ\_years + 0.035×exper − 0.0006×exper² + 0.01×tenure − 0.12×female + 企業規模の上乗せ（〜29人 0、30〜299人 0.05、300〜999人 0.10、1000人以上 0.18）+ 0.15×regular + ε。ε \~ N(0, (0.25 + 0.02×(educ\_years − 12))²)。切片 a は時給の中央値が約1,900円になるよう調整。educ\_years は12・14・16・18年を35・20・40・5%で割り当てる
- `training_rct` / `training_obs`：earn\_post = 150 + 0.8×prior\_earn + 5×educ\_years − 0.5×(age − 35)² / 10 + 30×treat + ε、ε \~ N(0, 60²)（単位：万円）。観察データの参加確率は logit(p) = −1 − 0.01×(prior\_earn − 250) − 0.02×(age − 35)
- `minwage_panel`：youth\_emp\_rate = 県効果 + 年効果（2020年に全国一律 −2pt） + 処置効果（経過0年 −0.5、1年 −0.8、2年以降 −1.0） + ε、ε \~ N(0, 0.6²)。処置前は平行トレンドが成り立つように作る
- `scholarship_rdd`：earn30 = 400 + 60×(gpa − 3) + 25×scholarship + ε、ε \~ N(0, 80²)、gpa \~ N(2.8, 0.5²) を0〜4に切り詰め

## 実装の進め方

土台→判定エンジン→データ→第1部の順に作り、第1部で学生の試用を挟んでから残り11部の教材を1部ずつ追加する。各マイルストーンは「受け入れ基準」を満たしたら次に進む。

| 段階 | 作るもの | 受け入れ基準 |
| --- | --- | --- |
| M0 土台 | Vite＋React＋TS、webR起動、エディタ、実行結果と図の表示、GitHub Pagesへの自動公開 | 公開URLで `1 + 1` とggplotの図が表示される。初回起動にかかる秒数を画面に出す |
| M1 判定エンジン | `r108check`（testthatでテスト）、step.yamlの読込とJSON Schema検証、判定の流れ、Rエラーの日本語化表、進捗保存 | 見本の3ステップで正解・不正解・エラーが正しく判定される（Playwright） |
| M2 データ | `data-raw/` の合成データ生成と公的統計の取得、コードブック | `Rscript data-raw/build_all.R` で全CSVが同じ内容で再生成される（チェックサム一致）。合成データに仕込んだ効果が推定で再現される（例：DIDの推定値が −0.8±0.2） |
| M3 第1部 | ステップ1〜9の本文と課題 | 全正解コードがテストを通る。各小課題にヒント3段階。教員レビュー済み。学生5人程度で試用 |
| M4 パッケージ検証 | 第2〜12部で使うパッケージをwebRで読み込む検証ページ | 動かないパッケージごとに代替を決め、この設計書の該当ステップを更新 |
| M5 第2〜5部 | ステップ10〜45 | M3と同じ基準 |
| M6 ローカル実行の仕組み＋第6部 | 確認スクリプトと修了コードの照合、ステップ46〜54 | 確認スクリプトをWindowsとmacOSで実行し、合格時だけコードが出る |
| M7 第7〜9部 | ステップ55〜81 | M3と同じ基準 |
| M8 第10〜12部 | ステップ82〜108 | M3と同じ基準 |

**教材を書くときの規則（Claude Codeへの指示に含める）。**

- 1ステップ＝1テーマ。新しく覚える関数は5個まで
- 本文は1,500〜2,500字、です・ます調、1文は短く。冒頭に「問い」、末尾に「卒論・実務での使いどころ」を1文
- 判定は正解コードの結果との比較で書き、正解の値を直接書かない
- 小課題は易しい順。最後の1問は前ステップの復習
- 使ってよいのは、そのステップまでに登場した関数だけ（`learn:` の累積で機械的に確認する）
- 1つの部を1つのプルリクエストにし、テストが通ってから教員がレビューする

リポジトリ直下の `CLAUDE.md` には次の内容を置く。

```markdown
# r108 — Rデータ分析108ステップ
- 仕様は docs/design.md（この設計書をMarkdownで書き出したもの）に従う
- 教材は content/steps/<3桁番号>/step.yaml と body.md。スキーマは schema/step.schema.json
- 新しいステップを作ったら必ず `Rscript tests/r/run_solutions.R <番号>` を通す
- 合成データの生成式は変えない。変えるときは設計書を先に更新する
- 1プルリクエスト＝1部（9ステップ）
```
